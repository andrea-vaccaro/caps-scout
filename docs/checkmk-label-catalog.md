# Checkmk plugin label catalog

Tracking document for the caps-scout long-term plan. This catalogs every host label
and service label currently generated by Checkmk's built-in plugins (source:
`~/workspace/check_mk`, survey taken 2026-08-27), so caps-scout's own `caps/*`
labels can be designed to sit alongside — and eventually cover gaps in — the existing
label surface.

All plugin families surveyed — this document is complete as of the date above.

## How Checkmk plugin labels work (observed conventions)

- **Host labels** (`HostLabel(key, value)`) attach to the *host* and are visible in
  discovery/inventory; they're what rulesets typically match against (e.g. "apply this
  rule to all hosts with `cmk/os_family:linux`").
- **Service labels** (`ServiceLabel(key, value)`) attach to a specific *service* on a
  host, not the host itself.
- Nearly every built-in label uses a `cmk/...` prefix. Sub-namespacing follows
  `cmk/<plugin-family>/<attribute>`, e.g. `cmk/podman/pod`, `cmk/kubernetes/namespace`.
- A generic passthrough exists: any agent plugin (including a fully custom one) can
  print a section literally named `<<<labels:sep(0)>>>` containing a JSON object, and
  Checkmk's core (`cmk/plugins/checkmk/agent_based/labels.py`) turns every key/value
  pair into a host label automatically — **no Python-side parser plugin is required**.
  This is the mechanism caps-scout should use.
- Several plugins propagate external label/tag systems wholesale under a reserved
  sub-prefix so they can't collide with or overwrite built-in labels — e.g. Kubernetes
  object labels become `cmk/kubernetes/label/<key>`, annotations become
  `cmk/kubernetes/annotation/<key>`, Proxmox VE tags become `cmk/pve/tag/<tag>`.
- A few labels are purely presence markers with a constant `"yes"` value (e.g.
  `cmk/ceph/mon`, `cmk/has_lldp_neighbors`) — this is the closest existing pattern to
  caps-scout's `caps/db/oracle: "yes"`-style detection labels.
- Some labels come from user-configured rulesets, not agent-reported data at all (e.g.
  systemd unit labels, `ps` process-discovery labels, network-interface discovery
  labels) — these are fully dynamic/user-defined and not really "detected" in the
  caps-scout sense.

## Implications for caps-scout

- **No existing plugin assigns a `cmk/os_family`-style label per *database engine*.**
  Every DB-adjacent plugin (`gcp_sql`, `oracle`, `mysql`, `postgres`, `mssql`, `mongodb`,
  `redis`, `db2`, `sap_hana`) monitors a specific, already-configured DB connection —
  none of them *detect* which DB engines are present on a host the way caps-scout is
  meant to. This is a real gap caps-scout fills, not duplicated work.
- **Precedent for presence-style labels exists and caps-scout should mirror it**:
  `cmk/ceph/mon: "yes"`, `cmk/has_lldp_neighbors: "yes"`, `cmk/docker_object: "container"`.
  → `caps/db/oracle: "yes"` fits this pattern exactly.
- **Decided: caps-scout emits a label for every capability it detects, regardless of
  whether a corresponding official Checkmk plugin is already installed on the host.**
  Plugin presence doesn't mean the plugin is configured or healthy, so it isn't a
  reason to withhold the capability label — the host inventory signal is useful
  either way.
- **`cmk/os_family` is the established name for OS identification** in the wider
  Checkmk label surface (core agent, Mobileiron, Kubernetes nodes, FritzBox,
  Redfish). None of these plugins detect the OS at runtime — each ships as a
  separate per-platform agent build (`agents/check_mk_agent.linux`, `.aix`,
  `.solaris`, `.macosx`, plus the Windows C++ agent), and each build simply
  hardcodes its own OS's name (`AgentOS: linux`, `AgentOS: aix`, etc.) — the build
  *is* the OS it targets. caps-scout mirrors this exactly: at compile time, via
  `cfg!(target_os = ...)`, it emits `caps/os_type/<name>: "yes"` for the same name
  Checkmk's own per-platform builds use (`linux`, `windows`, `macosx`, `solaris`,
  `aix`), following the same `caps/<family>/<attribute>: "yes"` presence pattern
  as the DB probes (e.g. `caps/os_type/linux: "yes"`). This is
  a deliberate exception to "caps-scout shouldn't duplicate what the core agent
  already provides" — it exists to give caps-scout's own probe set (which now spans
  DB engines and OS) a self-contained, one-`caps/*`-glance summary rather than
  requiring a cross-reference to `cmk/os_family`.
- **The generic `<<<labels:sep(0)>>>` passthrough is the correct integration point**
  (confirmed: core agent, FritzBox, Redfish, and AWS's account/service labels all use
  it directly) — caps-scout needs zero Checkmk-side Python code, exactly as scoped.
- **Namespacing precedent**: every built-in plugin uses `cmk/<family>/<attribute>`.
  caps-scout uses `caps/<attribute>` (flat) or `caps/<family>/<attribute>`
  (e.g. `caps/db/oracle`) to stay unambiguous and avoid ever colliding with a
  `cmk/*` label — labels only collide if the *key* matches, so as long as caps-scout
  never emits a bare `cmk/...` key this is inherently safe.
- **Decided: silence means "nothing detected."** caps-scout emits a label only when
  it detects a capability — it prints nothing at all when it finds none of the
  capabilities it checks for. This keeps the label surface itself as a signal of
  what's present, not a full inventory restated for every possible capability.
  Consequence: the *absence* of any `caps/db/*` label for a host, combined with
  caps-scout having run, means "none of the checked-for capabilities were found" —
  worth a clear README/doc note so this isn't mistaken for "caps-scout didn't run"
  (already added to the README).
